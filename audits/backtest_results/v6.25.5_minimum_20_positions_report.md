## Forensic root cause identified during this analysis: DETERMINISTIC CODE BUG

While investigating why trade frequency was so low relative to the owner's expectation (10+ positions/trading day), mining of the preserved 7-day decision journal found the exact mechanism:

**`EXHAUSTED_SAME_DIRECTION_REENTRY_BLOCK` (`backend/ea_code/XAUUSD_AI_Sniper_EA.mq5:19909-19920`) was not scoped to skip M30 mode, unlike its sibling gate `XAU_PostTradeCooldownActive()` immediately above it, which correctly was.**

Evidence from the 7-day journal (2026-07-08 → 2026-07-17):
- 65 distinct M30 candidates reached `result=EXECUTE` / `FINAL_ENTRY_ARBITER ... decision=ALLOW` / `BOT_DECISION: action=ENTER_ALIGNED_FULL_RISK` — i.e., passed every real approval gate.
- Only ~4 core trades actually opened in that window.
- 56 of the 65 approved-but-discarded candidates (86%) were vetoed one line later by `EXHAUSTED_SAME_DIRECTION_REENTRY_BLOCK`, logged with `M30_CANDIDATE_FINALIZED_NO_TRADE ... result=CANCEL_EXECUTION_NOT_CONFIRMED resurrectionAllowed=false` — a permanent discard, not a retry.

This is a leftover legacy-M10 re-entry-flow gate that never got the same M30-mode exemption its sibling received. It directly contradicts the owner's explicit rule: *"There must be no hidden cooldown"* / *"no extra retracement wait"* / *"a valid M30 candidate remains pending indefinitely"* — this gate was silently vetoing already-approved M30 candidates outside of M30's own architecture.

**Classification: DETERMINISTIC CODE BUG** (reproducible, root-caused, fix is a scoped one-line exemption mirroring an already-approved pattern in the same function — not a strategy-threshold change).

### Honest read: the fix is correct and proven; the resulting behavior is not yet good enough to deploy

**The fix itself is validated** — trade count went from 22 to 191 in the identical window (8.7x), directly confirming the root-cause diagnosis. This is not new/different logic; it's the M30 architecture's real behavior at its intended frequency, previously hidden by the bug.

**But net profit only grew from +$1,453 to +$3,479 (2.4x) while trade count grew 8.7x, and drawdown more than tripled (11%→36% balance, 19%→38% equity).** The extra volume of trades is not compounding into proportionally more profit — it's adding both more winners and more losers, with the losers large enough to consume most of the additional edge.

### Loss forensics — all 39 losses are genuine, clean structural stop-loss hits

Every one of the 39 losing trades in the post-fix 60-day run closed within a few cents of its recorded stop-loss price (e.g. SL 4185.87 → filled 4185.87 exactly; SL 4025.97 → filled 4025.80). **This rules out execution bugs, slippage anomalies, or SL-placement errors as the cause of these losses** — the broker-confirmed exit matches the EA's own structural invalidation level precisely in every case.

Loss size is highly consistent: median -$901.00 (range -$143.60 to -$2,027.65), which tracks the 10% risk-per-trade sizing. Win size is much more variable: median $247.45 but ranging from $0.48 to $1,581.30, split roughly evenly across small (<$150, 40 trades), medium ($150-400, 81 trades), and large (≥$400, 30 trades) buckets. This means the "winners cut short" narrative from the smaller 7-day sample does not fully hold at 60-day scale — many winners do capture large moves. The real problem is that **losses are consistently ~1R while wins are inconsistently sized**, so the realized payoff ratio depends heavily on how many trades land in the small-win bucket versus the large-win bucket in any given period.

**Classification: this pattern (Category H, "Normal Valid Loss" per the audit protocol's own taxonomy) requires a much larger, regime-diverse sample and genuine walk-forward validation before any exit/entry logic change is justified.** Nothing here points to a deterministic bug — the losses are clean, and win variability is a real property of the setups being taken, not a code defect.
