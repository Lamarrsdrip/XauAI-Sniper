# XauCloud Python → Node.js Backend Migration — Phase 1 Audit

Generated by grepping the actual source (not written from memory). Source of truth for the
Node.js/TypeScript (Fastify) rewrite. Every endpoint, collection, background job, and env var
below must have a 1:1 equivalent in the new backend before the Python backend is retired.

Owner directive: this is a **language migration only** — identical business logic, identical
API contracts, identical trading/exit/licensing/payment behavior. See conversation record for
the full 9-phase directive this document satisfies Phase 1 of.

## 5. Open question to resolve before Phase 2 starts (flagging per "stop and report conflicts" precedent from earlier in this project)

`backend/local_ai/service.py` and `remote_worker.py` are **standalone Python scripts** (`if __name__ == "__main__":`), designed to run as independent local processes on the trading VPS itself — not inside the FastAPI request/response cycle, not reachable from Hostinger at all. They exist for zero-latency, zero-API-cost local AI inference physically next to MT5.

**This means "require only Node.js in production" has two possible readings:**
- **(A)** Applies to the Hostinger-hosted web backend only — the VPS-local inference scripts are explicitly out of scope (they never touch Hostinger, they run on the *trading* VPS which already exists for MT5). Only `remote_relay.py`'s 4 cloud-relay routes need porting.
- **(B)** Applies to the entire codebase including the VPS-local scripts — would require also rewriting `service.py`'s local HTTP inference server and `remote_worker.py` in Node/TypeScript and redeploying them to the trading VPS.

Recommendation: **(A)**. These scripts don't run on Hostinger, don't affect the "no VPS for the website" goal, and aren't part of what serves `xaucloud.io`. Rewriting them would be pure extra risk to a working, unrelated, already-deployed local-inference system with zero benefit toward the stated goal (getting the *website/API* off Python hosting). Proceeding on this assumption unless told otherwise — will not silently rewrite `local_ai/service.py`/`remote_worker.py`.

**Resolved**: proceeded on (A). `remote_relay.py`'s 4 routes (`POST /local-ai/remote/submit`, `POST /local-ai/remote/result`, `POST /local-ai/worker/claim`, `POST /local-ai/worker/complete`) are ported to `backend_node/src/routes/localAi.ts` + `services/localAiSchema.ts` (Snapshot/Decision validation) + `services/localAiRelay.ts` (Ed25519 worker-signature verification via Node's native `crypto.verify(null, ...)`, tenant rate-limiting, job-lease state machine). Live-verified: schema validation, gold-symbol gating, tenant/global queue caps, job caching/idempotency, the static-secret and lease-state-machine paths (wrong lease → 409, correct lease → ACCEPTED), and the confidence-threshold TRUSTED/LOW_CONFIDENCE split. `service.py`/`remote_worker.py` remain untouched, as recommended. This closes the last open scope question — every `server.py` + `market_outlook_routes.py` + `remote_relay.py` route now has a verified Node.js counterpart (confirmed via automated route-table diff).
